# Hosting topology and deploys

Research run of 2026-11-18 (`agw research`, depth deep). Run status: partial. Citations grounded against fetched pages: 30/34. A citation ties a claim to a page; it is not proof. Treat everything under "Not verified" as a lead, and re-check a version number before pinning it.

## Bottom line

- **Marketing:** keep it on Cloudflare Workers static assets on the apex domain. Static requests are free and unlimited. Version URLs are public when enabled, so disable them or put them behind Cloudflare Access.
- **App:** serve the room SPA, the Elysia API and the WebSocket server from one VPS origin on a dedicated app hostname (for example app.<domain>), not under a path of the marketing domain. Route WebSockets through the Cloudflare proxy (supported on all plans, Proxy Read Timeout 125 s) with an application-level heartbeat well under 125 s. Keep a DNS-only hostname for WebSockets as a fallback if measurement shows the proxy hurts.
- **Deploys:** use drain-and-handoff with room snapshots in Postgres and an epoch (fencing) column per room, from day one. Clients reconnect with full-jitter backoff. Promise a few seconds of reconnect per room on deploy, not literal zero disruption.
- **Postgres:** PostgreSQL 18 (current minor 18.7) on the VPS, backed up with pgBackRest 2.60.1 (client-side encrypted, WAL archive plus full and differential backups to an S3-compatible bucket, monthly restore drill). Skip PgBouncer until connection count demands it.
- **Migration:** use pgloader 3.6.9 (the stable v3 line; v4 is pre-release) for the data, and hand-port the schema to Drizzle pg-core on the stable drizzle-orm 0.45.x line, not the 1.0 release candidate. Migrate only what a privacy-first, anonymous product actually needs.

**Must decide now (hard to retrofit):** the canonical app hostname (localStorage is per origin); the WebSocket protocol (version field, resume message, close codes, heartbeat); the room snapshot schema including the epoch column; Bun payload and backpressure limits; keeping previous content-hashed SPA assets across deploys; the backup encryption key (pgBackRest says encryption settings cannot be changed once set); the Postgres major version; the Drizzle version line.

## 2. Cloudflare Workers static assets

**Limits and pricing.** Requests to static assets are free and unlimited, and storing assets costs nothing. Requests that invoke Worker code are billed. Workers Paid has a $5/month minimum with 10 million requests included, then $0.30 per additional million; 30 million CPU-ms included, then $0.02 per additional million CPU-ms; no egress or bandwidth charge. Per Worker version: 20,000 files on Free, 100,000 on Paid, 25 MiB per file. The pricing page example that shows the static-only case includes the $5 subscription, and the pages I read do not say whether static-only works on Free. Note that `run_worker_first` on Free returns 429 instead of falling back to assets once the Free request limit is exceeded.

**Headers.** A `_headers` file allows up to 100 rules, 2,000 characters per line. Rules are applied in file order; `! Header` detaches one added earlier; joined values can break Cache-Control, so detach and re-set. Crucially, `_headers` rules are not applied to responses generated by Worker code, so SSR or proxied responses need headers set in code. The docs show an `X-Robots-Tag: noindex` rule for workers.dev hostnames, which keeps preview hosts out of search.

**Redirects.** A `_redirects` file allows 2,000 static and 100 dynamic redirects (2,100 total), 1,000 characters per rule, default status 302, splats and placeholders supported. Redirects run before headers. Redirects in `_redirects` do not apply to Worker-generated responses. Beyond 2,100, use Bulk Redirects.

**Preview URLs.** Now called Version URLs: `<version-prefix>-<worker-name>.<subdomain>.workers.dev`, created by `wrangler deploy` or `wrangler versions upload`. When enabled they are public; Cloudflare Access can protect them. They are not generated for Workers that implement a Durable Object, cannot use a custom domain, and their logs are not visible in Workers Logs, tail or Logpush. Version URLs are separate from the 'Previews' feature for isolated branch testing.

**SPA mode.** `assets.not_found_handling = 'single-page-application'` serves index.html with 200 for unmatched paths. With the `assets_navigation_prefers_asset_serving` flag (or a compatibility date of 2025-04-01 or later), navigation requests skip the Worker. `run_worker_first` with patterns gives explicit routing. Range requests return 200 with the full file, not 206, which matters only for media.

**Caution on skew.** The billing and troubleshooting page warns that HTML and asset requests may hit different versions after a deploy, and an older page can request a file missing from the new version.

## 3. Serving the room SPA from Workers or from the VPS

Serve it from the VPS. The SPA, API and WebSocket then share one origin: no CORS preflights, no cross-site cookie rules, the WebSocket URL is same-origin, and the SPA and server deploy together. Serving the SPA from Workers would create a second origin, which splits localStorage, cookies and CORS, and adds a Worker in the path of every API call.

The cost is the version-skew problem on the VPS itself. During a rolling replacement, the old container's index.html can reference bundles that the new container no longer has. Use content-hashed filenames and keep the previous release's assets served for at least one deploy cycle, the same discipline the Workers skew warning implies. This is design reasoning, not a sourced rule.

## 4. One origin with path routing versus an app subdomain

**Option A: path routing on one domain.** Marketing at example.com/, app at example.com/room/*, API at /api, WebSocket at /ws. To serve static marketing from Workers, a Worker must sit in front of the VPS for app paths (`run_worker_first` plus a fetch to the origin). That adds Worker billing and CPU on every app request, a hop of latency, and a copy of the security headers in code, because `_headers` does not reach Worker responses. A simpler variant serves marketing from the VPS too and drops Workers entirely.

**Option B: app subdomain (recommended).** Marketing on the apex (Workers); app on app.<domain> (VPS). Each keeps its own deploy cadence, and no Worker sits in the app path.

**SEO.** Google's FAQ says: 'choose whatever is easiest for you to organize and manage. From an indexing and ranking perspective, Google doesn't have a preference.' The SEO risk is duplicate hosts, not subdomains: Google says to 301 a duplicate domain to the preferred one. Pick one canonical marketing host (apex or www) and redirect the other, and keep the workers.dev hosts noindexed.

**Cookies.** Per MDN, a cookie without a Domain attribute is host-only and goes only to the host that set it. Domain=example.com shares it with all subdomains, so marketing and app would see the same cookie. The __Host- prefix requires Secure, no Domain and Path=/, which gives the strongest host-only session cookie. The room identity is a client-generated id in localStorage, so cookies are only needed for any server-side session, and host-only cookies are the right default.

**localStorage is per origin.** MDN says localStorage is for the document's origin and that data is specific to the protocol: http://example.com and https://example.com get different stores. app.example.com, example.com and www.example.com each get their own store. So the anonymous client id created on the app host does not exist on the marketing host, and changing the app hostname later orphans every user's id. This is the hardest-to-undo decision here. Choose the app hostname now and never change it.

**Embedding.** I did not research iframe embedding or frame-ancestors policy in this run. A poker room is normally opened as a top-level page, so this is low risk; set frame-ancestors 'none' on the app host unless embedding is a product goal (unverified, see below).

## 5. WebSockets through the Cloudflare proxy versus direct

**Through the proxy.** WebSockets are supported on all Cloudflare plans with the Network toggle on. Limits from the connection-limits page: Proxy Read Timeout 125 s (configurable only on Enterprise), Proxy Write Timeout 30 s, Proxy Idle Timeout 900 s (origin keep-alive, not the WebSocket idle timer), TCP connection establishment 19 s, request URL 16 KB, request headers 128 KB total, response headers 128 KB total. The WebSocket page says Cloudflare closes a connection when no data flows in either direction for a period, Enterprise can set a custom idle timeout, and the client should implement a heartbeat. Cloudflare may restart servers, which terminates WebSocket connections. The WAF inspects only the initial upgrade request. Workers WebSocket messages are not billed as requests, only the upgrade is.

**Heartbeat.** Send an application-level ping every 25 s (my recommendation; well under 125 s). Whether Bun's protocol-level pings count as traffic for Cloudflare's timer is not verified; use application messages to be safe.

**Direct.** A DNS-only hostname straight to Traefik removes the 125 s read timeout and the extra hop, but exposes the VPS IP, drops Cloudflare's DDoS and WAF in front of the WebSocket, and needs its own Let's Encrypt certificate through Traefik. For a 2 to 30 person room with small messages, the proxy's latency cost is small; the decisive factor is whether abuse protection matters more than a few milliseconds. My recommendation: proxy by default, measure p95 reconnect and message latency from real clients, and keep the direct hostname in reserve.

**Bun and Elysia settings.** Bun's `idleTimeout` defaults to 120 s (range 0 to 960) and Bun pings the client shortly before the timeout; `maxPayloadLength` defaults to 16 MB (larger messages close with 1009; corrected by `v9-api-ws`: Bun 1.4 ends the connection without a close frame, read as 1006); `backpressureLimit` defaults to 16 MB. For a poker protocol set both far lower (for example 16 KB payload; backpressure of a few hundred KB). `ws.pause()` and `ws.resume()` apply TCP backpressure. `server.stop(true)` closes each WebSocket with code 1001; `server.stop()` leaves them open. Elysia's WebSocketHandler accepts the same options, including `idleTimeout`, `maxPayloadLength`, `backpressureLimit`, `closeOnBackpressureLimit` and `sendPings`.

## 6. Zero-downtime deploys of the stateful WebSocket server

Room state lives in process memory, so two containers cannot both own a room. Correctness must not depend on routing. Use epoch fencing, and treat routing only as a way to reduce disruption.

**Storage choice.** Postgres (already in the stack) as the room store. Snapshots are small (a room has at most 30 people and a handful of votes), and state changes in planning poker are sporadic (a join, a vote, a reveal), so write-on-change with a short coalescing window (about 250 ms, my proposal) is well within what Postgres handles. Redis adds a component with no benefit at this scale. Disk on the VPS loses state with the disk.

**Schema.** rooms(id, state jsonb, version bigint, epoch bigint, owner text, updated_at, expires_at). Every write is `UPDATE rooms SET state = $1, version = version + 1 WHERE id = $2 AND epoch = $3`. If zero rows update, the instance no longer owns the room: close its sockets for that room with an application code and stop.

**Claim on restore.** When a client joins a room that is not in memory, the instance runs `UPDATE rooms SET epoch = epoch + 1, owner = $me WHERE id = $2 RETURNING state, epoch`. The old owner's next write fails, so there is no split-brain even if the old container is still alive.

**Deploy sequence.**
1. Start the new container; it passes health checks and starts claiming rooms as clients arrive.
2. The old container stops accepting new room claims and sends a 'moved' notice to each connected client with a jittered reconnect delay.
3. It snapshots each room, closes sockets with a custom code (4000+ range, app-defined) and exits once rooms are empty or a deadline passes. Bun's `server.stop(true)` provides a 1001 close for anything left.
4. Clients reconnect through Traefik to the new container, which claims the room and sends full state.

Traefik's own lifecycle options (`transport.lifeCycle.graceTimeOut`, default 10 s; `requestAcceptGraceTimeout`, default 0 s) apply to Traefik's own shutdown, not to backend WebSocket drain. The application must do the drain. Docker's container stop timeout must exceed the drain deadline; Docker's default is 10 s (from memory, not re-read here).

**Numbers (my arithmetic).** 500 rooms of 10 people is 5,000 clients. Reconnecting in a 5-second jitter window is about 1,000 upgrades per second, which needs a load test on the target VPS. A 30-second window cuts that to about 170 per second but extends the outage. AWS's architecture blog found that jitter cut client calls by more than half at 100 contending clients and that no-jitter exponential backoff was the worst option.

**Client resume.** Send a protocol version, the client id from localStorage, the room id and the last version seen. Server replies with full state, which is small, so skip diffs. Backoff: full jitter, base 500 ms, cap 30 s, reset after 60 s of stable connection; after a 'moved' notice, wait a uniform 0 to 2 s. Re-send the local vote from localStorage keyed by room, round and client id, so votes are idempotent and a reconnect cannot lose one. Give up on auth and room-gone codes. Votes are hidden until reveal, so snapshots contain votes and should have a retention limit (privacy decision).

**Test before trusting.** Run a deploy under synthetic load, kill the old container mid-reveal, and check that no vote is lost and no room is owned by two instances (check epoch and version).

## 7. Postgres on the VPS

**Backups.** pgBackRest 2.60.1 is the more conventional choice here. Its user guide documents S3 support, client-side repository encryption (the encryption settings are fixed once the repository is created), repo-bundle, and repo-block (recommended at least v2.52.1), zstd compression, archive-async with a spool path, and `info --output=json` for monitoring. Its cron example runs a weekly full backup and daily differentials. It warns that its archive-timeout (default 60 s) is different from PostgreSQL's archive_timeout, which forces WAL switches; set archive_timeout to bound data loss.

WAL-G 3.0.10 is a single Go binary with S3 and PostgreSQL streaming documented. Its S3 backup-name reservation requires S3-compatible storage with conditional writes, so check the provider before choosing WAL-G. Its `--wait-for-archive` flag and `--permanent` backups are useful; defaults include 16 upload streams and 1 GB tar bundles.

Recommendation: pgBackRest, with a monthly restore drill into a scratch VM, and an alert on the age of the last full backup and on the archive gap in `info` output. Whichever tool you pick, the restore drill matters more than the tool.

**Pooling.** A single app container with a driver pool of around 10 connections does not need PgBouncer. During a deploy, old and new containers briefly double the connections, still a small number. Add PgBouncer 1.26.1 later if connection count grows. If you do add it in transaction mode, set `max_prepared_statements` (default 200 since 1.24.0): PgBouncer tracks protocol-level named prepared statements, but SQL-level PREPARE/EXECUTE are forwarded untouched.

## 8. MariaDB to Postgres migration

**Data.** pgloader's own page calls MySQL and MariaDB 'the flagship path' with enum-to-type translation, TINYINT(1) to boolean, zero-date handling and .my.cnf credential lookup. The MySQL docs list the default WITH clause (no truncate, create tables, include drop, create indexes, reset sequences, foreign keys, downcase identifiers, uniquify index names). The `tinyint-to-boolean` and `zero-dates-to-null` casts are shown commented out or as options, so you must enable them deliberately. `schema only` and `data only` let you rehearse in two steps. The docs do not say whether the live load reads a consistent snapshot: run it against a read-only copy or a dump taken at a quiet moment.

**Drizzle port.** Port the schema by hand to pg-core: mysqlTable to pgTable, AUTO_INCREMENT to identity, DATETIME to timestamp with time zone (decide what time zone the old values meant), TINYINT(1) to boolean, ENUM to pgEnum, JSON to jsonb. Use the 0.45.x stable line. The 1.0 release candidate changes the relational API and includes breaking changes, so it belongs in a later upgrade. Generate the initial migration from the pg-core schema and diff the resulting database against the pgloader output (schema-only pg_dump) before cutover.

**Checklist.** Rehearse twice on a copy. Compare row counts and a checksum per table. Check timestamps and time zones by sampling. Reset sequences (pgloader does this by default). Migrate only what the product needs: the rewrite is an anonymous, privacy-first planning poker tool, so old per-room data may not need to come across at all. Analytics on Parquet and FastAPI are not affected by the database change.

## 9. Recommendation

Workers static assets for the marketing site on the apex (with a single canonical host and noindexed workers.dev hosts); the app on app.<domain> from the VPS, with the SPA, API and WebSocket on one origin; WebSockets through the proxy with a 25 s application heartbeat; drain-and-handoff deploys with epoch-fenced Postgres snapshots and full-jitter client resume; PostgreSQL 18 with pgBackRest and a restore drill; pgloader for data and a hand-ported Drizzle schema on 0.45.x.

## 10. Main tradeoffs

- Subdomain versus path: a separate origin for marketing costs the cross-origin split of localStorage and cookies, but avoids Worker billing and latency in the app path and keeps deploys separate.
- Proxy versus direct WebSocket: proxy gives DDoS and WAF protection and a 125 s read timeout that the heartbeat must respect; direct removes that but exposes the VPS.
- Postgres versus Redis for room state: Postgres adds write load to your primary database and is simpler; Redis would add a component for little gain at this scale.
- Epoch fencing versus simple restart: fencing adds an update per claim but makes correctness independent of load-balancer behaviour.
- Snapshot retention versus privacy: keeping snapshots helps resume and debugging, but they hold hidden votes. A short TTL on expires_at is the privacy-friendly default.
- pgBackRest versus WAL-G: pgBackRest has the more conventional operational model; WAL-G is lighter but needs conditional writes from the object store.
