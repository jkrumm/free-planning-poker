# Languages from day one: catalogue, routing, workflow

Research run of 2026-11-20 (`agw research`, depth standard). Run status: ok. Citations grounded against fetched pages: 20/20. A citation ties a claim to a page; it is not proof. Treat everything under "Not verified" as a lead, and re-check a version number before pinning it.

## Bottom line

- **Library (part 1):** Paraglide JS (npm latest 3.2.2) fits a bundle-sensitive, strictly typed React SPA best: it compiles messages to typed functions that tree-shake per message, and it is the only candidate whose sources list Astro alongside Vite-React, so one catalogue could serve both. Confidence is medium. The main risk is maturity. The July 2026 comparison listed 2.22.0 and about 567 GitHub stars; the registry now shows 3.2.2, so pin the exact version and budget for API churn. Lingui 6 is the conservative compile-time alternative. react-i18next is the safe default but ships the whole catalogue. react-intl is the ICU-purist choice at the largest bundle. use-intl was not assessed.
- **Astro routing (part 2):** Astro 6 documents locale prefixes, an unprefixed default locale, per-locale fallback (redirect or rewrite), browser-language detection and URL helpers. I did not find a built-in hreflang generator in the pages I read, and nothing on how content collections behave with partial translations.
- **Day one (part 3):** Externalise every visible string from the first commit, lint against literal JSX text, use ICU plurals and native Intl APIs, and decide the URL and locale-negotiation rules now. Most of the specifics (RTL, text expansion, CJK, lint rules) were not researched and are listed under unverified.
- **SEO (part 4):** Google's scaled-content policy targets mass pages with little added value, not translation as such. Translated pages are not duplicates. hreflang must be complete and reciprocal. Launch the app with English and German, but the marketing site with one complete language until German pages are fully translated and reviewed.
- **Workflow (part 5):** Keep ICU-style JSON in git, use an LLM for first drafts with native review, and use Weblate's hosted libre plan if the project qualifies. Crowdin's open-source form asks for community criteria a solo maintainer may not meet. Tolgee's free tier comes from a secondary source only.

## 1. Message-catalogue libraries

Sizes are min+gzip figures as the sources print them. Sources disagree, so treat them as ranges.

- **Paraglide JS (inlang):** latest 3.2.2 on npm. A July 2026 comparison puts it at about 1 kB per locale, tree-shaken per message, and cites a vendor benchmark of 47 kB against i18next's 205 kB at 5 locales x 100 messages. Missing or renamed keys are compile errors. Lists Vite, TanStack Start, React Router, Astro, SvelteKit, Vue and Solid as supported. Message format is ICU-style, but the depth of ICU support was not verified. Per-locale chunking was not verified.
- **Lingui:** @lingui/core latest 6.12.0 on npm. The July comparison gives about 10 kB total and 2 to 3 kB runtime. Macros extract messages at build time and the compiler strips unused ones; tree-shaking depends on how the code is written. ICU-style macros; RSC support since v5. Astro support was not verified.
- **react-i18next:** latest 18.0.3 on npm. The July comparison gives 15 to 22 kB. A 2021-dated SimpleLocalize table gives about 9 kB, so sizes depend on setup. Loads the full JSON catalogue, so there is no per-message tree-shaking. Its own format is custom, with ICU only through a plugin, and key type safety is opt-in. Largest ecosystem, about 10.5M weekly npm downloads.
- **react-intl (FormatJS):** the July comparison gives version 10.1.16 (not checked on the registry) and 13 to 20 kB. Full ICU MessageFormat (plurals, select, rich text) on native Intl. Key type safety is moderate. About 3.4M weekly downloads.
- **use-intl:** not assessed in this run; no size, version or maintenance data.

For scale: 15 to 22 kB is 8 to 12 percent of the 180 kB entry budget before any app code (derived from the figures above). Paraglide's per-message output stays small as the catalogue grows, which is the strongest argument for it under this budget.

For this SPA, the ranking on size and tree-shaking is Paraglide, then Lingui, then react-intl, then react-i18next. On ICU completeness it is react-intl first. Lazy loading one locale per chunk was not verified for any library; measure it on the built entry before committing.

## 2. Astro 6 i18n routing

What the Astro docs provide (read in full):

- Locales and a defaultLocale. `prefixDefaultLocale` defaults to false, so the default locale sits at the root and others get a prefix. With true, every URL is prefixed and unprefixed URLs return 404 unless a fallback applies. `redirectToDefaultLocale` can be added in that mode.
- Custom locale paths: several browser codes (fr, fr-BR, fr-CA) can map to one URL prefix such as /fr/.
- Fallback per locale, for example fr falling back to es. Each missing route is generated and either redirects (default) or rewrites to the fallback page (`fallbackType: 'rewrite'`, added in v4.15). A fallback route is therefore not a translated page.
- Browser detection: `Astro.preferredLocale` and `Astro.preferredLocaleList` derive from Accept-Language. `Astro.currentLocale` comes from the URL and falls back to the default locale.
- Helpers: `getRelativeLocaleUrl`, `getAbsoluteLocaleUrl` and `getAbsoluteLocaleUrlList`.
- Per-locale domains need `output: server`, a site URL, and an adapter such as Node or Vercel. Static output cannot use them.
- A `routing: manual` mode lets you write your own middleware.

Sitemap integration (@astrojs/sitemap v3.7.6): the docs describe an `i18n` option taking `defaultLocale` and a `locales` map. The page I read was cut off before explaining its output, so whether it emits xhtml:link alternates is unverified.

hreflang: the pages I read show no hreflang tag helper. You can build the alternate list from `getAbsoluteLocaleUrlList`, but that is a manual step, not a documented feature.

Limits for partially translated content:

- Fallback creates routes for untranslated pages, so the site's URL list grows with every fallback route.
- Behaviour for content collections (per-entry language, missing entries) was not researched.

## 3. Decisions to make on day one

Sources were read only for the Astro routing and Google hreflang items. The rest is engineering judgement, not sourced in this run.

- **String externalisation:** no literal user-visible text in JSX from the first commit, including placeholder and aria strings. The lint rule against literal JSX text was not verified: check oxlint's rule list first, then the ESLint i18n plugins.
- **Plurals and parameters:** ICU plural and select messages, never concatenated fragments. Paraglide, Lingui and react-intl use ICU-style messages (per the July comparison).
- **Numbers, dates, relative time:** use Intl.NumberFormat, Intl.DateTimeFormat, Intl.RelativeTimeFormat and Intl.PluralRules with the active locale, and keep formatting out of translator-facing strings.
- **RTL:** use CSS logical properties (inline-start, inline-end) in the Tailwind 4 design system, so Arabic or Hebrew can be added later without rewrites.
- **Text expansion:** leave room for longer strings (German and Portuguese are usually longer than English). The percentage budget was not verified; test with pseudo-locales.
- **CJK:** line breaking and a font-fallback stack for Chinese and Japanese were not researched.
- **Locale negotiation:** the site's URL prefix is authoritative. In the app, a stored user choice comes next, and Accept-Language only suggests a language on first visit. Astro's preferredLocale is the server-side equivalent.
- **URL strategy for the unprefixed app:** keep room URLs locale-free so shared links are stable, and store the language choice in a cookie or localStorage. The marketing site keeps Astro's scheme: default language at the root, others under a prefix.

## 4. SEO for translated pages

- **Scaled content:** Google's guidance (last updated 2026-10-01) says generating many pages without added value may violate the scaled-content-abuse policy. It also requires manual fact-checking and review of AI-generated content, including metadata and alt text. The guidance does not single out machine translation, so the inference is that value and review matter, not the origin of the text. I did not find a study showing whether machine-translated pages rank or are penalised; that is unverified.
- **Duplicates:** localised versions are only duplicates if their main content stays untranslated. Translated pages are therefore not duplicates in the sense Google describes.
- **hreflang rules:** each version lists itself and every alternate, with fully qualified URLs. Pairs must link back to each other or the tags are ignored. x-default marks the fallback page. Use ISO 639-1 language codes with optional ISO 3166 region codes; es-419 is not supported, and a region code alone is invalid. Google says HTML tags, HTTP headers and sitemaps are equivalent, so pick one.
- **Pitfalls (partly judgement):** listing a fallback redirect as an alternate; missing return links after adding a language; mixing template-only translation with full translation.
- **One language or two:** the site should launch with one complete language. Two languages with half-translated pages create hreflang gaps and thin fallback routes. The app's roughly 250 strings are cheap to ship in two languages on day one.

## 5. Translation workflow for a solo maintainer

- **Formats:** the July comparison ties Lingui and react-intl to PO through Crowdin, and react-i18next to JSON. XLIFF and ICU-JSON support in Weblate and Crowdin was not verified.
- **LLM first pass:** not researched. Judgement: keep the English source in git, generate drafts as pull requests, and have a native speaker review German and each later language. Quality and cost were not verified.
- **Weblate (primary page read):** hosted strings = source strings x (translation languages + 1). Derived: 250 app strings x (6 + 1) = 1,750 hosted strings for seven languages, far under the 10k plan's list price of EUR 47 a month. The page says the Libre plan is free for public libre projects, with the same limits as the 160k plan, and that self-hosting is free under GPLv3. Check eligibility on Weblate's side before relying on it.
- **Crowdin (primary form read):** the open-source programme is free. Eligibility requires an OSI-approved licence, three months of work, an active community of collaborators, regular builds, and a News section on the website. In return you contribute translations to Crowdin Global TM and get access to its neural MT. A solo maintainer may not meet the community criterion. A secondary search snippet puts Crowdin's free plan at 60,000 hosted words; this is unverified.
- **Tolgee:** a secondary snippet says the core is Apache 2.0 and the free cloud plan has 30,000 words and 3 seats. Not checked against Tolgee's own terms.

## Recommendation

1. Spike Paraglide JS with one React route and one Astro page before committing, and check the built entry against the 180 kB budget. Pin the version.
2. If the spike fails, use Lingui 6. Choose react-intl only if strict ICU matters more than size.
3. Use one message source for both the app and the site, so translators work in one place.
4. Ship the app in English and German on day one. Launch the site in English and add German pages only when they are complete and reviewed, with hreflang only between pages that exist.
5. Put translations on Weblate hosted under the libre plan if eligible. Otherwise self-host Weblate or work with files in git. Use LLM drafts with native review.
