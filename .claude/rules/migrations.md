# Migrations

Two server versions run against one database during every deploy: RollHook starts the new container before it stops the old one. A migration therefore has to work with the code of the release before it.

## The rule

- **Expand, ship, contract.** Add a column, a table or an index first; ship the code that uses it; remove what the old code read in a later release. A migration that drops or renames something the previous release reads is refused by review.
- **Forward only.** No down migration; a mistake is fixed by the next migration.
- Migrations are generated by drizzle-kit (0.31.x, with drizzle-orm 0.45.x, both pinned exactly) into schema `fpp`, with the journal in the same schema. Never edit a migration that has merged. Before changing anything in `apps/api/src/db`, Read its `AGENTS.md`.
- Use nothing newer than PostgreSQL 16: the factory's step host runs 16, CI and production 18.
- A migration is tested against a private cluster from `startPostgres()` in a `*.server.test.ts`, never against the mini's `fpp` database or production.
- `room_snapshot` is UNLOGGED and holds hidden votes and seat-token hashes: nothing but the owner process reads it, and no migration copies it elsewhere. History names a seat by its index and never a person (`docs/v9/ARCHITECTURE.md`, Data model).
- No row deletes rounds or votes by age; `visitor_day` rows older than 13 months are the one scheduled deletion.

## Why

`docs/v9/ENGINEERING.md`, Migrations; `docs/v9/ARCHITECTURE.md`, Data model and Server (ownership and handoff). This is where migrations live and run for the factory too: `project.yaml` has no key for them.

## The check

The server tier in `make check` applies every migration to an empty cluster and runs the store's tests on it. Expand-before-contract has no script: review checks each migration against the code of the release before it.
